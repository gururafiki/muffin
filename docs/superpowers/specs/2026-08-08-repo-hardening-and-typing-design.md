# Repo hardening + typing cleanup + upstream triage — 2026-08-08

Three asks, one design, because they turned out to share a root cause: **nothing
was checking anything on a pull request**, so both a dependency hazard and a class
of runtime bug reached `main` unobserved.

## Ask 1 — bring the other repos up to muffin-agent's standard

### What existed

| Repo | Dependabot | CodeQL | Ruleset | Security updates | PR checks |
|---|---|---|---|---|---|
| `muffin-agent` | pip only | ✅ actions+python | "Main branch rules" | ✅ | CodeQL only (`NEUTRAL` on dep diffs) |
| every other repo | ❌ | ❌ | ❌ | ❌ | ❌ |

Secret scanning + push protection were already on everywhere.

### What shipped

**Tiered protection**, chosen so the thin Dockerfile wrappers and the umbrella
keep their direct-push workflow:

- **Tier 1** — `muffin-ui`, `muffin-deployment`: exact clone of muffin-agent's
  ruleset (no deletion, no force-push, Copilot review on push, code-quality,
  CodeQL gate at high-or-higher/errors, PR required with 0 approvals) **plus a
  required status check** pointing at a new quality workflow.
- **Tier 2** — `openbb-mcp-docker`, `agent-chat-ui-docker`, `nuq-postgres-docker`,
  `muffin` (umbrella): no-deletion + no-force-push + the CodeQL gate. Direct push
  preserved.

The umbrella could not get CodeQL: GitHub reports `languages: []` for it, so
default setup is not available. It carries guardrails only.

**Dependabot, per repo, with `groups: minor-and-patch`** so each ecosystem yields
about one PR a week instead of a dozen:

| Repo | Ecosystems | Notable exclusions |
|---|---|---|
| `muffin-agent` | pip, github-actions | `mcp` (safety bound), both git-URL fork pins. No `docker` — CI generates the Dockerfile via `langgraph dockerfile`. |
| `muffin-ui` | npm, docker, github-actions | the whole Expo SDK family (`expo`, `expo-*`, `react`, `react-dom`, `react-native`, `react-native-*`) — those versions are chosen as a set by `expo install`. No `gradle`: `android/` is generated by `expo prebuild` and untracked. |
| `muffin-deployment` | terraform, pip (`config/opensandbox`), github-actions | No `docker` — it builds no images. |
| `openbb-mcp-docker` | pip, docker, github-actions | — |
| `agent-chat-ui-docker` | docker, github-actions | No `npm`: the Dockerfile git-clones upstream and uses upstream's lockfile. |
| `nuq-postgres-docker` | github-actions | Complete set. No Dockerfile and no manifest — it sparse-checkouts `apps/nuq-postgres` from firecrawl/firecrawl. |
| `muffin` (umbrella) | gitsubmodule (monthly) | Bookkeeping only; deploys are driven by each build repo's `deploy` dispatch, so a stale pin never blocks a release. |

Plus Dependabot **security** updates enabled on all seven (needs
`PUT /vulnerability-alerts` first — `automated-security-fixes` silently no-ops
otherwise).

**New quality workflows** where none existed:

- `muffin-agent/.github/workflows/quality.yml` — ruff lint, ruff format, mypy,
  `pytest -m unit`, and the resolve+import smoke test, on `pull_request`.
- `muffin-ui` — `npm run check` (tsc + eslint over the whole tree + the offline
  timeline/skeleton scripts).
- `muffin-deployment` — `terraform fmt -check -recursive`,
  `init -backend=false` + `validate`, and `ansible-playbook --syntax-check` with
  the pinned collections. All credential-free and incapable of touching real infra.

**No workflow carries a `paths` filter.** A filtered workflow never reports on a
PR that misses the filter, which leaves a PR blocked forever on a required check
that will never arrive.

## The hazard this uncovered

Dependabot PR #145 (merged 2026-08-08 10:31 UTC) widened `mcp<2` to `mcp<3` —
reopening the 2026-07-28 outage class where mcp 2.0.0 dropped `RequestContext`,
every graph failed to load, and the deployed API sat at 0/1.

Three independent failures had to line up:

1. **The cap was reachable.** `mcp<3` permits mcp 2.x. The only thing excluding it
   was `langchain-mcp-adapters` 0.3.2 declaring `mcp>=1.24.0,<2.0.0` itself — but
   the floor was `>=0.3.1`, which has no such cap. → Floor raised to `>=0.3.2`,
   making the capped version a guarantee rather than resolver luck.

   > **Correction.** The first version of this section justified the floor by
   > saying the runtime installs with `-c /api/constraints.txt` and could
   > therefore land on 0.3.1. That file constrains neither `mcp` nor
   > `langchain-mcp-adapters` — checked in the base image, 36 lines, neither
   > present. The floor is still right; that reason was not.

2. **Dependabot did not know the bound was a guard** → an `ignore` entry for
   `mcp`. **Superseded — see below.** The bound itself turned out to be the
   problem.
3. **The guard that existed ran too late.** The resolve+import smoke test lived
   only in `build-image.yml` on push-to-main, and `cancel-in-progress` killed
   #145's run when the next merge landed 12 seconds later. The only PR check was
   CodeQL, which reports `NEUTRAL` on a dependency-only diff. → The smoke test now
   also runs on `pull_request`, and `build-image.yml` no longer cancels `main`
   builds.

### Follow-up: the bound was deleted, not guarded

Reviewing the result raised the right question — does `mcp<3` do anything? It does
not. The only binding constraint on mcp is adapters' own `mcp>=1.24.0,<2.0.0`
(strictly stronger); the sole other declaration in the tree is `anthropic`'s,
under an extra we do not install.

And it could not block what its comment claimed: the outage was **mcp 2.0.0**, and
`<3` *permits* 2.x. The moment it became the binding constraint it would have
allowed exactly the version that took the API to 0/1. It excluded only mcp 3.x,
which does not exist. **A bound that cannot block the thing it names is worse than
no bound, because reviewers read it as protection** — the old comment even
conceded "does NOT by itself exclude mcp 2.x", which was the tell.

So the direct bound is gone and the cap lives in one place, upstream. Verified by
resolving in the runtime base image exactly as prod does, with the bound removed:
**mcp 1.29.0, adapters 0.3.2, langgraph 1.2.10**, and `criteria_analysis.graph` /
`personas_council.council_graph` / `auth` all import. The Dependabot `ignore` for
`mcp` went too — dead config once no direct bound is declared.

**Accepted trade-off, deliberately.** Real mcp-2 support is tracked upstream in
langchain-mcp-adapters#578. When it ships, adapters relaxes its cap and mcp 2.x
arrives through a routine Dependabot bump of adapters — nothing here stops it. The
resolve+import smoke test gates the import-time break that caused the original
outage, but it imports four modules and does **not** exercise MCP tool calling,
which is where a subtler mcp-2 regression would surface. `roadmap.md` records the
action: exercise a real OpenBB/Firecrawl tool path by hand on that PR.

## Ask 2 — typing and linting

`muffin-ui` and `muffin-deployment` were already clean (`tsc` passes, terraform
`fmt` clean). `muffin-agent` had 7 unformatted files and **50 mypy errors**, with
no `[tool.mypy]` section at all — documented in CLAUDE.md, enforced nowhere.

Now zero, and gated in CI. The pass found two genuine defects:

### 16 CLI commands were dead on arrival

Every data-collection streamer plus `criterion` and `evaluate` built a
`ModelConfiguration` and passed it to a factory that takes a `RunnableConfig`. The
factory's first statement calls `from_runnable_config(config)` →
`config.get("configurable")` → `AttributeError: 'ModelConfiguration' object has no
attribute 'get'`.

**Why it hid:** `BaseConfiguration.from_runnable_config` had no return annotation,
so mypy inferred `Any`, and `Any` satisfies every parameter. Only the two sites
that *also* misspelled the factory name were visible. Annotating it `-> Self`
turned the other 14 into errors immediately. **Keep that annotation** — it is the
thing that makes this defect class visible, and it is the same class CLAUDE.md
records for the retired `run_deep_agent_node` wrapper.

### A latent production crash in a persona scorer

`stanley_druckenmiller` read `prices_1y` (`list[dict[str, Any]]`, inner values
uncoerced by Pydantic) with a bare comprehension, so a weak LLM extracting `close`
as `"185.23"` raised `TypeError: '<=' not supported between instances of 'str' and
'int'` — the identical failure that took down the AMZN council run through
`nassim_taleb`. Taleb was fixed then; Druckenmiller reads the same dicts and was
missed, even though `_to_float`'s docstring said to call it "at every site that
reads those dicts". `to_float` + a new `clean_series` now live in
`tools/scoring_helpers.py`, and 4 regression tests were verified to fail against
the old code with the exact production TypeError.

### The 20-error bulk was one design mistake

All 19 `AnalystSignal` subclasses narrow `evidence` from `dict[str, Any]` to their
own model, and a subclass cannot retype an inherited field. `AnalystSignal` is now
`Generic[EvidenceT]` with a PEP 696 `default="dict[str, Any]"`, so a bare
`AnalystSignal` is unchanged. Declarations only — nothing in `src/` reads
`.evidence`.

### Accepted suppressions

Three, each narrow and explained at the site: an `OpenAIEmbeddings(base_url=...)`
Pydantic-alias false positive (verified against the installed class —
`openai_api_base` has `alias="base_url"` and `populate_by_name=True`); the
`EvidenceT` default factory; and two plain list/dict variance casts.

mypy is deliberately **not** strict. `disallow_untyped_defs` across 176 modules
would bury findings like the two above under thousands of annotation chores.

### One finding worth keeping

While reviewing #8538, `eliornl` reported that in stored deepagents data `files`
reads back `{}` while `messages` in the same read is complete — **the bug is
per-channel**. Our fork-pin guard only asserted on `messages`, so it would not
have caught that. `files` is a `DeltaChannel` on our pinned deepagents 0.6.12 too
(`FilesystemState.files`, `DeltaChannel(_file_data_delta_reducer)`), so
`tests/test_fork_pins.py` now asserts a second delta channel hydrates in the
nested namespace.

**Verified against production afterwards (credentials supplied mid-session): the
symptom does not reproduce, and cannot today.** Across a `stock_evaluation` thread
(13 `tools:<uuid>` subagent namespaces) and a `criteria_analysis` thread (15
namespaces), **no namespace anywhere has a non-empty `files` channel**. The
suggestive case — `ticker_classification`, which reads **63 messages alongside
`files == {}`**, exactly eliornl's shape — turns out to be legitimately empty: its
only tool calls are `task`, `write_todos`, and the structured-output schema tool,
with **zero filesystem tool calls and zero "tool result too large" offload
markers**. So nothing wrote to `files` for the read to lose.

Our agents route durable state through `/scratch/` (`StateBackend`) and
`/memories/` (`StoreBackend`) via `CompositeBackend`, not the plain `files`
channel, and no tool result crossed `FilesystemMiddleware`'s 20k-token offload
threshold in these runs. We become exposed the moment one does — which is what the
new guard covers at the mechanism level.

Two API gotchas found while doing this, both worth not re-deriving:

- **Cloudflare returns `403` with body `error code: 1010` for `Python-urllib`'s
  default User-Agent.** That is a bot-signature block, *not* an auth failure —
  identical requests via `curl` succeed. Send a browser-like `User-Agent`.
- `/threads/search` answers with CF Access headers alone, but `/threads/{id}/history`
  additionally needs the Supabase user Bearer token (GoTrue password grant).

### Separately observed, not investigated

In the `stock_evaluation` thread, **12 of 13 `tools:<uuid>` namespaces return zero
snapshots** — they resolve (no `Subgraph tools not found`, so the deepagents pin is
deployed and working) but yield empty history. Only the data-validation subagent
returned anything. The root state reads `channels: []`, consistent with the
already-documented "a deep agent's `values.messages` is empty — read transcripts
from `tasks[].result`" correction. Whether the 12 empty namespaces are the same
known behaviour or something else was **not established**; do not assume.
